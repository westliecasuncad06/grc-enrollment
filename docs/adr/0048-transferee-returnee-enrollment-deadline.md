# ADR 0048 — A New Transferee or Returnee Sees Only Enrollment and Has 7 Days to Be Approved

**Status:** Accepted
**Date:** 2026-10-14
**Related:** ADR 0026 (credit mapping), ADR 0030 (Registrar approval), ADR 0037 (Admission checklist), ADR 0043 (pay-first enrollment).

**Amended 2026-10-15 (ADR 0050):** decision 2 is replaced: the deadline is cleared when the enrolment is finished and paid (`ConfirmPayment`), not at the Registrar's approval, and a restricted student sees Enrollment and Grades (not Enrollment alone).

## Context

The owner asked that a newly created Transferee or Returnee account does not show every portal option. Until the Registrar approves their enrollment they can only do the things that lead to it: credit mapping, choosing subjects, the queue number and the payment, all of which sit inside the Enrollment page. The page also has to say that the account is deactivated in 7 days if the credit mapping and the enrollment, through payment, are not finished. The deactivation is real. The other options appear once the Registrar approves the enrollment, which is the last step. A deactivated student is reactivated by going through Admission again: a new setup, the same process as creating the account.

## Decisions

1. **One nullable date on the profile.** `student_profiles.enrollment_deadline_at` (migration `2026_10_14_000001`, reversible). `ProvisionStudent` sets it to 7 days after the moment Admission creates the account, only for a Transferee or a Returnee (`StudentType::hasEnrollmentDeadline()`, `ENROLLMENT_DEADLINE_DAYS`). Every account that existed before the migration, and every other student type, has `NULL`, so nobody existing is restricted or deactivated by it.
2. **The Registrar's approval clears it, for good.** `TransitionEnrollment` clears the date on `registrar_approve`, for Registrar Staff and Registrar Head alike (both decide approvals, ADR 0030). The profile is locked before the enrollment, the order every other pay-first action uses (PROFILE, then ENROLLMENT, then sections), so an approval cannot deadlock with the Cashier confirming the same student's payment, and the overdue command below locks the profile in the same order, so an approval that lands first wins. A rejection or a void does not clear it. For a Transferee the payment is already made when the Registrar approves; a Returnee pays after the approval (ADR 0043 keeps the ordinary order for them), so the one rule for both is that the clock ends at the Registrar's approval, and a Returnee who then does not pay is handled by the existing 3-day auto-void of an unpaid enrollment, not by deactivating the account.
3. **Automatic deactivation.** `students:deactivate-overdue` runs hourly (like `enrollments:auto-void`; `--dry-run` lists the accounts). For an active account whose date has passed it puts the account back in the state it had before its setup: `disabled`, `account_setup_completed_at` cleared, every login token deleted, one `user_account.deactivated` audit row with the reason. It acts as the first Registrar Head, like the auto-void command, and fails without changing anything when there is none. It is idempotent, and an account that never finished its setup is already unusable and is left alone. The date is kept after a deactivation: it is how the next invitation knows the 7 days ran out. A student can therefore use the account for up to an hour after the date passes.
4. **Reactivation is Admission's setup invitation.** Because the deactivated account is a pending account again, Admission's existing "Resend setup email" is the re-admission: the student gets a new code, sets a new password, and is active again. When the old date has passed the invitation also starts a fresh 7 days (audited in the invitation row as `enrollment_deadline_restarted`); an invitation sent while time is left never extends it, and an account without a date never gets one. `ActivateStudentAccount` refuses a setup code after the date, with a message that sends the student to Admission. The Super Admin's own reactivation already refuses a pending account with "Resend the setup invitation instead", so every route ends in the same step. Admission's requirements checklist is not reset by a re-admission: the same screen is used to correct it, and no institutional rule says otherwise.
5. **What a restricted student sees.** The profile API returns `enrollment_deadline_at`. While it is set, `PortalShell` shows only Enrollment in the sidebar (no GRC Connect home link), sends every other page, including `/portal`, to `/portal/enrollment`, and shows a banner on every page: "This account will be deactivated in N days (date) unless your credit mapping is done and your enrollment is completed through payment. The other options unlock once the Registrar approves your enrollment." The link to Academic Records on the Enrollment page is hidden meanwhile. Admission's directory shows a "Deadline passed" badge on a deactivated account instead of "Awaiting setup". While the profile is loading, or if it cannot be read, nobody is restricted: this is a convenience for the student's own data, not an access control, and the API itself is unchanged.

## Consequences

- Needs the migration on every environment before the code; nothing existing changes until Admission creates the next Transferee or Returnee.
- The 7 days are counted from the account's creation by Admission, not from the student's first login, so a student who opens the setup email on day 6 has one day. Admission can admit them again.
- No email warns the student before the deactivation (not asked for).
- The front-end gate is not an authorization boundary: a deactivated account has no token; an active restricted account can still call the API for its own records, as before.
